# clean — Code Quality Audit Skill

## When to invoke

When the user asks to audit code quality, check best practices, review code cleanliness, or generate a quality report for this project.

---

## Instructions

You are a senior software engineer performing a thorough code-quality audit of this FastAPI + LangGraph project. Your job is to read the actual source files, identify real issues (not hypothetical ones), and produce a prioritised `report.md` at the project root.

### Step 1 — Read the project

Read every source file in these directories in order. Do **not** skip files.

```text
main.py
app/config/
app/models/
app/repository/
app/services/
app/routers/
app/workflows/mail_assistant/graph/
app/workflows/mail_assistant/nodes/
app/workflows/mail_assistant/agents/
app/workflows/mail_assistant/prompts/
app/utils/
alembic/versions/
pyproject.toml
```

Use `Glob` to list every `.py` file under `app/` first so you don't miss anything, then `Read` each file fully.

### Step 2 — Evaluate against these dimensions

For every file, check the criteria below. Record only **real findings** — quote the exact file path and line numbers.

#### A. Architecture & Layer Integrity

- Does each layer only call the layer directly below it? (Router → Service → Repository → Model — never skip layers)
- Are there any direct DB queries in routers or nodes?
- Are there any business-logic decisions inside repository methods?

#### B. LangGraph / Agent Patterns

- Does every node function accept `(state: AgentState)` and return a `dict` (partial state update)?
- Are there any nodes that mutate state in-place rather than returning a dict?
- Does the supervisor's retry logic use `time.sleep` on the hot path? (flag if called without async equivalent)
- Are agent tool functions decorated with `@tool` and properly typed?
- Are conditional edges using named constants from `node_names.py` or raw strings?

#### C. Error Handling

- Are bare `except Exception` blocks present without re-raise or specific logging?
- Are LLM JSON-parse failures surfaced to the caller, or silently swallowed?
- Are database errors caught at the repository layer and re-raised with context?
- Are there any places where a `None` return from a DB query is used without a null-check?

#### D. Type Safety

- Are all function signatures annotated (parameters + return types)?
- Is `AgentState` updated with new keys without adding them to the TypedDict definition?
- Are SQLAlchemy models missing column-level type annotations (`Mapped[...]` style)?

#### E. Security

- Are any secrets (API keys, passwords) hardcoded or logged?
- Is user input from the email body used in a database query without sanitisation?
- Does `gmail/auth.py` store or log raw tokens?
- Are CORS or authentication middleware applied to production routes?

#### F. Code Duplication & DRY

- Do `issue_handler.py`, `asset_request_handler.py`, and `software_request_handler.py` (nodes and agents) share large blocks of identical code that could be extracted?
- Are prompt strings defined inline in node files instead of in the `prompts/` directory?
- Are repository methods duplicated across multiple repository files?

#### G. Naming & Readability

- Are there abbreviations that are unclear (`IssuHandlerAgent` — typo in `issue_handler.py`)?
- Are constants defined as magic strings/numbers inline rather than in `constants/`?
- Do file and class names follow the project's established conventions (snake_case files, PascalCase classes)?

#### H. Database / Migration Hygiene

- Do Alembic migrations use `batch_alter_table` for SQLite compatibility, or are they Postgres-only (note it explicitly)?
- Are all ORM relationships explicitly typed and back-populated?
- Are indexes defined for frequently queried columns (email on `User`, status on `AssetItem`)?
- Are any columns nullable that should be `NOT NULL`?

#### I. Testing

- Are there any test files? If not, flag it.
- Are the `/mock/*` router endpoints the only test mechanism? Suggest unit tests for repositories and service layer.

#### J. Dependency & Configuration

- Are there unused imports in any file?
- Are `pyproject.toml` dependency version pins overly loose or missing?
- Is `deepagents` (the custom dependency) actually used? If so, document where; if not, flag as unused.

### Step 3 — Produce the report

Write `report.md` to the **project root** (not inside `app/`). Structure it exactly as follows:

```markdown
# Code Quality Report

_Generated by the /clean skill. All findings reference actual file paths and line numbers._

## Summary

| Dimension | Issues Found | Severity |
|-----------|-------------|----------|
| Architecture & Layer Integrity | N | High/Med/Low |
| LangGraph / Agent Patterns | N | ... |
| Error Handling | N | ... |
| Type Safety | N | ... |
| Security | N | ... |
| Code Duplication & DRY | N | ... |
| Naming & Readability | N | ... |
| Database / Migration Hygiene | N | ... |
| Testing | N | ... |
| Dependencies & Configuration | N | ... |

## Findings

### [SEVERITY] Title of Issue

**File:** `path/to/file.py:line_number`
**Dimension:** Which dimension from Step 2
**Problem:** Exact description of what is wrong, quoting the offending code inline if short.
**Recommendation:** Concrete fix with a short code example where helpful.

---

_(repeat for every finding, ordered: Critical → High → Medium → Low)_

## Positive Observations

_(3–5 things the project does well — be specific and cite files)_

## Recommended Priority Order

1. Fix all Critical and High security findings first.
2. ...

_(ordered action plan the team can follow directly)_
```

**Severity guide:**

| Severity | Examples |
|----------|---------|
| Critical | Hardcoded secret, SQL injection risk, data loss risk |
| High | Silent error swallowing, missing null-check on DB result, layer violation |
| Medium | Missing type annotation, code duplication, missing index |
| Low | Naming inconsistency, unused import, missing back-populate |

### Step 4 — Finish

After writing `report.md`, tell the user:

- The total number of findings by severity
- The single most important thing to fix first
- The path to the report file

Do **not** apply any fixes yourself — this skill is read-only and report-only.
